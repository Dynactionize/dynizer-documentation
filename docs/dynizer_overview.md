# Dynizer

## Introduction
Enterprises increasingly struggle with fragmented information—databases, document repositories, emails, reports, logs, and application data that coexist without a unifying structure. Conventional approaches treat structured and unstructured sources separately, relying on different tools and models for each.
Dynizer addresses this challenge through a *universal*, *compact semantic model* that can represent any domain's information using the same core primitives.

## Dynizer (Semantic Database)

The uniquess of Dynizer uniqueness lies in linking each meaningful piece of data—such as a phrase in text or an element from a database column—to one of four basic semantic categories (or also known as component types (CT)): Who, What, Where, and When. This creates a structured model that formally represents the content of all linked data sources and documents, exposing the connections between them.

### Running Example (John Doe medical document)

Consider a Dynizer system dedicated to storing patient medical information. Among the documents is a physician's report on a consultation for a patient named "John Doe" in file "P-014_08102025.doc". A snippet of the notes reads:

```
Patient: John Doe
DOB: 12/04/1985
Visit Date: 08/10/2025

Patient reports persistent lower back pain for the past 4 months, worsened by prolonged sitting. MRI shows mild disc herniation at L4–L5. No neurological deficits observed. Conservative treatment recommended, including physical therapy and NSAIDs. Patient expresses concern about long-term mobility.
```

Dynizer semantically analyzes document and database content to uncover connections. It also provides a suite of out-of-the-box functionalities for efficient access to analyzed information.

### Example Dynizer Outputs

Based on the John Doe medical document, Dynizer can automatically generate the following:

- **Dynamic summaries** of documents, such as:
  - Clinician summary (diagnosis + treatment)
  - Patient-friendly summary (plain language)

- Customizable **pseudonymized versions** of documents:
  By replacing "John Doe" and DOB with neutral identifiers for safe sharing, this removes direct identifiers and supports GDPR compliance workflows.

- Medical **keywords** and **key concepts**:
  Lower back pain, disc herniation, MRI, physical therapy, NSAIDs

- **Categorization** of documents into **predetermined categories**:
  Leveraging predefined clinical taxonomies (e.g., ICD, internal hospital categories), terms can be assigned to categories like orthopedic consultation, chronic pain, diagnostic imaging performed, etc.

- **Dynamic highlighting** of the most **important/critical concepts** in a document.

- Detailed clinical **analysis of activities** and **sentiments** in a document.

## Dynizer Architecture

Dynizer comprises three primary functional layers:

1. **Semantic Abstraction Layer**: Maps all information into Who, What, Where, When, and Actions.
2. **Core Semantic Index**: A compressed bit-matrix engine storing relationships between elements.
3. **Processing & GenAI Integration Layer**: Includes the Analyzer, struct2sent, and MAG/GenAI services.

These layers form a unified semantic platform for modeling, indexing, and surfacing insights from enterprise information sources.

### Semantic Abstraction Model

#### Core Concepts

Dynizer models information using four semantic dimensions:
- **Who**: e.g., Physician, Patient
- **What**: e.g., Sickness
- **Where**: e.g., Cabinet, City
- **When**: e.g., Consultation date

These are grouped into Actions, representing meaningful events or contextual structures. Each information element is tagged with a semantic category (e.g., Who) and a domain-specific label (e.g., doctor, patient, location, document section).

#### Universality Across Sources

This model applies to:
- Relational databases
- Semi-structured JSON/XML
- Unstructured documents (PDF, Word, text)
- Content extracted by Analyzer
- Structures generated by struct2sent

A database row and a sentence from a PDF produce the same semantic action structure. The abstraction is domain-agnostic, requiring no predefined ontology or graph schema.

### The Core Semantic Index (Bit-Matrix Engine)

#### Unique Element Identification

Each unique (value + semantic category) pair is stored once and assigned a unique ID. Examples:
- "John Doe" as Who -> Who-ID
- "Consultation" as What -> What-ID

#### Bit-Matrix Relationship Storage

Relationships are stored in highly compressed bit matrices representing element co-occurrences within Actions. Key features:
- Matrices capture relationships across Who, What, Where, When, and Actions.
- Queries operate on matrices first, resolving into IDs.
- Values are fetched only after semantic layer matches.

#### Efficiency and Security Through Separation

Data values reside in relational tables, while relationships are in bit matrices. This enables:
- Minimal duplication
- Secure multi-tier deployment
- Data remaining in customer environments while Dynizer acts as an index.

## Integration with Existing IT

Dynizer seamlessly integrates into existing IT infrastructure, exchanging data with over 250 sources with minimal effort. It automatically handles common formats like Word, PDF, RTF, ODF, Excel, and others.

## Advanced Application of Dynizer (GenAI)

Dynizer supports intelligent interaction with popular GenAI models for natural language question-answering based on its data.
